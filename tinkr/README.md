# tinkr

Dockerized AI agent that compiles natural-language prompts into
position-independent native code (PIC blobs). The generated code resolves
OS APIs through a runtime-supplied "seed" of function pointers and
syscall conventions, so the same blob ABI works on Linux, macOS, and
Windows targets.

```
prompt ──► claude + skills ──► .c source
                                    │
                                    ▼
                          clang+SheLLVM+llc+link+extract
                                    │
                                    ▼
                                 blob.bin
                                    │
                                    ▼
                          downstream loader populates
                          seeds and calls into byte 0
```

## What's in the box

| target                         | format        | linker     | extractor                        | tested via                       |
|--------------------------------|---------------|------------|----------------------------------|----------------------------------|
| `*-linux-gnu` (4 archs)        | ELF           | ld.lld     | `objcopy --only-section=.blob`   | qemu-user in container           |
| `arm64-apple-macos`            | Mach-O        | ld64.lld   | `tools/extract-macho-segment.py` | Mac host (loader_macos)          |
| `x86_64-apple-macos`           | Mach-O        | ld64.lld   | same                             | needs Intel Mac (builds clean)   |
| `x86_64-pc-windows-msvc`       | PE/COFF       | lld-link   | `tools/extract-pe-sections.py`   | qemu-x86_64 + ms_abi loader      |

Four supported Linux archs: x86_64, aarch64, arm-eabihf, i686.

## Quick start

```bash
# Build images. First run takes ~10 min (LLVM + SheLLVM compile).
docker compose build

# Run hello on the host arch.
docker compose run --rm dev make -C examples/hello_linux_syscall run

# Same but cross-arch.
docker compose run --rm dev bash -c '
  ./scripts/build-shellcode.sh examples/hello_linux_syscall/hello.c /tmp/hello.bin x86_64-linux-gnu
  ./tools/build-loader.sh /tmp/loader x86_64-linux-gnu
  qemu-x86_64-static /tmp/loader /tmp/hello.bin
'
```

## Running the agent

Put your Anthropic API key in `.env`:

```
ANTHROPIC_API_KEY=sk-ant-...
```

Then:

```bash
# Native arch (host = container arch).
docker compose run --rm agent \
  "write 'hi' to stdout via the linux write syscall"

# Cross-target + execute it.
docker compose run --rm agent --target x86_64-linux-gnu --exec \
  "write 'hi' to stdout via the linux write syscall"
```

For macOS and Windows targets the agent produces the blob but can't
execute it in-container (macOS) or runs under qemu+ms_abi (Windows).
See the test-loader section below.

## The seed contract

The blob's entry signature is fixed:

```c
int entry(struct seeds *s, void *args, size_t args_len);
```

`struct seeds` is autogenerated from `skills/`. Each library
(libc, kernel32, libobjc, Foundation, ntdll, libSystem) is one sub-struct
of typed function pointers; the loader populates whichever sub-structs
make sense for its platform.

```c
struct linux_libc {
    long (*write)(int, const void *, size_t);
    int  (*open)(const char *, int, unsigned int);
    int  (*close)(int);
    int  (*dup2)(int, int);
};

struct windows_kernel32 {
    int   (*WriteFile)(void *, const void *, unsigned int, unsigned int *, void *);
    void *(*GetStdHandle)(unsigned int);
    /* ... */
};

struct seeds {
    struct linux_libc       *libc;
    struct macos_libsystem  *libsystem;
    struct macos_libobjc    *libobjc;
    struct macos_foundation *foundation;
    struct windows_kernel32 *kernel32;
    struct windows_ntdll    *ntdll;
};
```

Syscall-style skills don't appear in the seed — they emit inline asm
directly. Cocoa methods don't appear in the seed either — they go through
`s->libobjc->objc_msgSend`.

There's no sidecar metadata alongside the blob. `seeds.h` IS the contract:
agent and loader compile against the same header.

## Skills

YAML, one file per (function, platform, lib) under
`skills/<platform>/<lib>/<function>.yaml`. Three lowering strategies share
a common core (`name`, `platform`, `lib`, `description`, `signature`,
`example`, `notes`):

**`lowering: indirect_call`** — function pointer in the seed.
```yaml
seed:
  header: linux_libc
  field: write
  access: "s->libc->write"
signature:
  return: { c_type: long, on_failure: "-1, errno set" }
  params:
    - { name: fd, c_type: int }
    - { name: buf, c_type: "const void *" }
    - { name: count, c_type: size_t }
```

Variadic functions (e.g. `objc_msgSend`, `NSLog`) add `seed.type: "void *"`
so the seed field is opaque and the caller MUST cast at the call site.

**`lowering: syscall`** — inline asm with per-arch helpers.
```yaml
arch:
  arm64:   { syscall_number: 64, helper: "static long sys_write(...) { ... svc #0 ... }" }
  x86_64:  { syscall_number: 1,  helper: "static long sys_write(...) { ... syscall ... }" }
```

**`lowering: objc_msgsend`** — macOS Cocoa method.
```yaml
class_name: NSString
selector: "stringWithUTF8String:"
receiver_kind: class            # or: instance
requires:
  - macos/libobjc/objc_getClass
  - macos/libobjc/sel_registerName
  - macos/libobjc/objc_msgSend
helper: |
  static void *NSString_stringWithUTF8String(struct macos_libobjc *o,
                                             const char *utf8) {
      void *cls = o->objc_getClass("NSString");
      void *sel = o->sel_registerName("stringWithUTF8String:");
      typedef void *(*msg_t)(void *, void *, const char *);
      return ((msg_t)o->objc_msgSend)(cls, sel, utf8);
  }
```

Skill `notes:` are always block scalars (`notes: |`) — bullet chars,
backticks, and colons in raw YAML lists hit pyyaml's reserved-character
rules.

### Regenerating seeds.h

`seeds.h` is autogenerated. After adding or modifying skills:

```bash
docker compose run --rm --entrypoint python3 agent /work/tools/gen-seeds-h.py
```

### Building Tailor with Tinkr's compiler

The dev container also mounts the sibling `../tailor` directory at `/tailor` and
exposes `tools/build-tailor.sh`:

```bash
docker compose run --rm dev tools/build-tailor.sh exe /tmp/tailor-profile x86_64-linux-gnu
docker compose run --rm dev tools/build-tailor.sh bytecode /tmp/tailor-profile.bin arm64-apple-macos
```

`exe` uses the container LLVM toolchain to build Tailor as a normal executable.
`bytecode` compiles Tailor's bytecode entry through the existing SheLLVM
pipeline and emits raw native bytes only.

See [`docs/tailor.md`](docs/tailor.md) for the full Tailor compiler, context,
and Soldir handoff workflow.

### Generating Context-Aware Blobs

Tailor can emit a resolver profile of function hashes and module-relative
offsets. Pass that profile to the agent so generated code resolves functions
from `args` as `struct tinkr_context *` instead of relying only on `seeds.h`:

```bash
python3 ~/personal/andromeda/tailor/tools/tinkr-symbols.py ~/personal/andromeda/tinkr/skills \
  > ~/personal/andromeda/tinkr/tailor-symbols.txt
~/personal/andromeda/tailor/bin/tailor-profile \
  --symbols ~/personal/andromeda/tinkr/tailor-symbols.txt \
  > ~/personal/andromeda/tinkr/tailor-profile.json

docker compose run --rm agent \
  --context-profile /work/tailor-profile.json \
  --skills macos/libSystem/write \
  --target arm64-apple-macos \
  -o /work/context-write.bin \
  "write 'hi' to stdout using the supplied resolver context"

~/personal/andromeda/tailor/bin/tailor-run ~/personal/andromeda/tinkr/context-write.bin --verbose
```

The resolver ABI is defined in `tinkr_context.h`. The runtime loader passes the
context as `args` to the normal Tinkr entry signature.

For API-free verification, build `examples/context_write/hello.c` and execute
it with `~/personal/andromeda/tailor/bin/tailor-run`; the fixture resolves `write` from
`struct tinkr_context` and prints `context hi`.

### Validating skills

Three layers, increasing cost:

**1. Structural** — `tools/validate-skills.py`. Parses every YAML,
checks the schema per lowering type, confirms `seed.access` is
consistent with `seed.header`/`field`. ~1s for 150 skills.

**2. Compile** — `tools/validate-skills.py --compile`. Synthesizes a
minimal C source per skill (references the seed field for
indirect_call; pastes the helper for syscall/objc_msgsend) and runs
it through clang+SheLLVM. Catches type mismatches between skill
signatures and `seeds.h`. ~30s for 150 skills.

```bash
docker compose run --rm --entrypoint python3 agent /work/tools/validate-skills.py --compile
```

**3. Golden tests** — `tools/golden_test.py`. Drives the agent
end-to-end with curated prompts in `agent/golden/v1.yaml`, builds
the blob, executes it (qemu wrapper for cross-arch), and compares
captured stdout + exit code to expected. Catches ABI bugs that
only surface at runtime (e.g. the NSLog variadic-pointer footgun).
~1-2 min and ~$0.50 in API tokens for the v1 suite.

```bash
python3 tools/golden_test.py
```

[`SKILLS.md`](SKILLS.md) — auto-generated browsable index of every

### Generating a skill from docs

`agent/skill_gen.py` produces YAML skills from a function name and
(optionally) a URL or doc snippet:

```bash
# From Claude's training knowledge (good for well-known APIs):
docker compose run --rm skill-gen \
  --platform linux --lib libc --function read

# From MSDN docs:
docker compose run --rm skill-gen \
  --platform windows --lib kernel32 --function VirtualFree \
  --doc-url https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualfree

# Then regenerate seeds.h.
```

## Test loaders

| loader                          | runs on   | populates                                  |
|---------------------------------|-----------|--------------------------------------------|
| `tools/loader.c`                | Linux     | `linux_libc` (just `write`)                |
| `tools/loader_macos.c`          | macOS     | `libsystem`, `libobjc`, `foundation`       |
| `tools/loader_pe_on_linux.c`    | Linux     | win64 `kernel32` via ms_abi → libc shims   |

Mac loader is compiled on the host (no Apple SDK in the container):

```bash
clang -O2 -I . -o tools/loader_macos tools/loader_macos.c
./tools/loader_macos blob.bin
```

PE loader runs inside the container under qemu when the host is arm64:

```bash
docker compose run --rm dev bash -c '
  ./scripts/build-shellcode.sh examples/hello_windows/hello.c /tmp/blob.bin x86_64-pc-windows-msvc
  clang -O2 --target=x86_64-linux-gnu -fuse-ld=lld -I /work -o /tmp/loader_pe /work/tools/loader_pe_on_linux.c
  qemu-x86_64-static /tmp/loader_pe /tmp/blob.bin
'
```

No Wine needed: our blobs have zero PE imports — every "Win32 call"
goes through the seed — so the ms_abi loader just translates win64 ABI
calls into Linux libc.

## Constraints encoded in the agent's system prompt

The agent emits C source that satisfies SheLLVM's `Postcheck` pass:

- Single translation unit, only `#include "seeds.h"`.
- Exactly one function with `__attribute__((annotate("shellvm-main")))`,
  signature `int entry(struct seeds *s, void *args, size_t args_len)`.
- No `extern` declarations. All externals come through `s` or are inline-asm
  syscalls.
- No file-scope variables. String literals must be local to `entry`
  (SheLLVM's `global2stack` pass relies on this to lift them to the stack).
- No TLS, no thread-locals.
- Helper functions are fine; SheLLVM's `flatten` pass inlines them.

## Pinned versions

- LLVM 16 (from apt.llvm.org on debian:bullseye-slim — matches SheLLVM's own canonical Dockerfile)
- SheLLVM master (override with `--build-arg SHELLVM_REF=<sha>` for reproducibility)

## Limitations

- macOS arm64 blobs deployed under hardened runtime require MAP_JIT +
  `pthread_jit_write_protect_np` instead of the simple
  `mmap RW → mprotect RX` dance our test loader uses.
- The agent does single-shot codegen; no retry-on-build-failure yet.
- Skill validation (`tools/validate-skills.py`) catches structural and
  compile-time issues, but ABI bugs (like calling a variadic function
  through a non-variadic typed pointer on arm64 Apple) only surface
  when the blob actually runs.

## TODO — real-target validation

These are blocked on hardware we don't currently have access to:

- **macOS x86_64**: builds clean, but no Intel Mac to execute the
  resulting Mach-O blob. The x86_64 Mach-O path went through
  `__literals` extraction and the build verifies, but runtime
  behavior is unconfirmed.
- **Windows native**: PE blobs run inside the container via the
  `ms_abi` wrapper loader + qemu-x86_64-static. A real Windows host
  would let us validate against the actual `kernel32`/`ntdll`/`ws2_32`
  exports rather than libc shims with win64 calling convention.

When these become available, run the existing `examples/hello_*` blobs
on the native target as a smoke test, then build a representative blob
per sub-struct (e.g. windows kernel32 `CreateFileW + WriteFile +
CloseHandle`) and confirm correct behavior.
